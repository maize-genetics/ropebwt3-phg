Scoring model — imputation outcome per read

Every read falls in exactly one outcome (sum to 100%):

outcomemeaning
recallplaced at the correct locus & true founder present — what imputation needs
founder-dropout criticalplaced right, but the true founder is missing — its support is lost
misplaced criticalevidence emitted at the wrong locus — false support elsewhere
unmappedno confident placement (UNPLACED/MULTI) — evidence lost

founder-dropout and misplaced are the errors that hurt imputation. For recall reads the true founder is already present; the other founders are a secondary specificity measure: IBS founders = non-source founders identical over the read span (identity-by-state, inherent ambiguity); spurious founders = founders added only because error shortened the match (not truly consistent — a specificity cost the CRF's multihot absorbs, it does not drop the true founder); missed-IBS = IBS founders missed (~0 with strict attribution).

Read this the right way: the imputation-critical errors stay near zero — founder-dropout is 0.0% at every rate and misplaced ≤1.3%, so the true founder is essentially always recovered at the right locus. The big-looking spurious founders curve (0→61%) is the benign one: the true founder is still present, there are just extra founders that error made consistent over a shortened match — honest ambiguity the CRF's multihot absorbs, alongside ~1.1/read of genuine IBS founders. Strict per-read attribution (refmap --ps4g-reads) makes missed-IBS a true 0.0%.

Raising the minimum exact-core length barely lowers spurious founders (31→28% @1%, 49→42% @2%) or misplaced, but craters recall and raises unmapped (to 22% at 2% error). The single- longest-core design has a specificity floor -l cannot break — spurious founders come from the core matching other founders over its span (conserved exons), not short off-target hits. Keep -l low; specificity needs chaining across the read's SMEMs, not a higher floor.

Exon-spanning (junction) reads are badly served

8k reads, up to 2 junctions, 1% error (48% within-exon, 49% one-junction, 3% two-junction).

read classreadssegs/readrecall (near-exon)coverage capvalid emitted base

two-junction2113.0095.7%≤33%5.4%

Two independent failures on spliced reads: structural — stock refmap emits one position/read, so a read spanning N exons covers at most 1 (per-segment coverage capped at 1/N); and coordinate — the whole-read [cL,cR) is extrapolated as if contiguous, invalid across a junction, so the one emitted base usually lands off the exons (valid-base rate 58%→8.5%). On this 51%-junction set overall recall falls 99→88% and misplaced rises 0.6→12%. Fix = splice segmentation: emit each colinear SMEM at its own exon start base.

Next: unite information across a read's SMEMs

Both results point to the same fix: stop using one core per read. Collect all of a read's SMEMs, chain the colinear ones, refine the founder set across the chain (lowers spurious without raising -l, because a founder must be exact over the whole read), and emit per exon segment at each segment's own start base (covers all exons, valid positions). Python prototype over ropebwt3 mem first, then a C --smem-out. Design in rnaseq_ps4g/NEXT_STEPS.md.
